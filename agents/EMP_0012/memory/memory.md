## 产品边界经验

### Radar 产品定义 (2026-03-09, 首份正式产品定义)
- 产出 docs/products/radar.md — 模块间接口定义 + 反馈回路详设 + 迭代路径
- 关键设计：星型拓扑约束 — 模块间无直接通信，全部经 Mason 中转
- 反馈回路三种行为数据：dismiss（显式负面）/ read（显式正面）/ 隐式跳过（未操作即低兴趣）
- 教训：产品定义文档应在功能开发之前完成，这次是功能先做了再补定义，导致定义只能描述现状而非引导设计

### Agent 角色更新建议 (2026-03-09)
- 识别两个归属真空：视频管线（mason-hub/skills/ 15+ 文件无人负责）、分析代码（策略决策权 vs 维护权不分）
- 建议方式：出建议稿到 docs/plans/，Mason 批准后再改 agent 文件 — 这是正确的流程，不越权
- 教训：归属真空往往不是一个人的问题，而是职责矩阵的缺失。用 RACI 矩阵（谁决策/谁执行/谁咨询/谁知会）比口头分工更清晰
