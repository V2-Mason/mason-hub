### Escalation 架构总览

agent 体系采用四层 debug escalation 架构，确保代码问题被系统性地处理，不遗漏也不越级：

### Escalation 架构（含链式触发）

```
Layer 0: Dev (EMP_0005) — 自动修复（每次最多 3 轮）
  │ 代码修改 → dev-verify-loop（语法→模块测试→回归）
  │ 最多 3 轮自动修复
  │ 3 轮失败 → git checkout 恢复 + audit.jsonl 记录 + Slack 通知
  │ → 自动触发 PM（无需人工干预）
  │
  ▼ repair_failed（自动链式触发）
Layer 1: PM (EMP_0001) — 评估分类（对同一任务最多重分配 Dev 2 次）
  │ 运行 check-escalation.sh → 检查 can_retry
  │ can_retry=true + A/B 类：输出 ACTION → 自动触发 Dev
  │ can_retry=false 或 C/D 类：输出 ACTION → 自动触发 Platform Dev
  │ E 类：输出 ACTION → Slack 通知 Mason
  │
  ▼ 架构/测试问题 或 PM 重试耗尽（自动链式触发）
Layer 2: Platform Dev (EMP_0002) — 跨域修复（最多 3 轮）
  │ 修复 skills 脚本、测试框架、agent 配置
  │ 修复后运行 dev-verify-loop 验证
  │ 无法修复 → Slack 通知 Mason（链结束）
  │
  ▼ 无法解决
Layer 3: Mason — 人工决策
  需求调整、架构重设计、或搁置任务
  Mason 的介入不可被自动触发（必须通过 Slack 通知后人工决策）

横向: SRE (EMP_0004) — 全局监控
  持续监控 audit.jsonl + chain depth + token 消耗
```

**链式触发规则**：
- Dev 失败 → 自动触发 PM（不需要人工干预）
- PM 决策 → 通过 ACTION 输出自动触发下一步
- Platform Dev 失败 → Slack 通知 Mason（链结束）
- 全局 chain depth 上限：10（防止无限递归）

**完整 Escalation 链路及次数限制**：
- Layer 0 Dev：每次分配最多 3 轮自动修复
- Layer 1 PM：对同一任务最多重新分配给 Dev 2 次
- Layer 2 Platform Dev：最多 3 轮自动修复
- Layer 3 Mason：人工决策

**最坏情况下的自动消耗上限**：
- Dev: 3 轮 × 3 次（首次 + PM 2 次重分配）= 9 轮
- PM: 3 次评估
- Platform Dev: 3 轮
- 经验总结: ~3 次
- 总计: ~15 次 claude -p 调用，~216k tokens
- 超过此上限必定交给 Mason

**Escalation 原则**：
- **不跳层**：Dev 不直接找 Mason，PM 不跳过 Platform Dev
- **带上下文**：每次 escalation 必须附上 audit.jsonl 记录和已尝试的方向
- **有时限**：每层处理不超过 1 个工作周期（session），超时自动升级
- **可追溯**：所有 escalation 都记录在 audit.jsonl 中和 logs/tasks/ 中
- **有上限**：每层有明确的重试次数限制，防止无限循环
