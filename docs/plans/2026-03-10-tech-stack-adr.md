# Architecture Decision Record — 技术栈选型

> 日期: 2026-03-10
> 状态: 活跃文档，每个组件达到天花板时更新
> 目的: 记录每个技术选择的原因、天花板、替换条件，避免"不知道为什么这么做"

---

## 编排层

### 组件: bash scripts + cron + systemd
- **选择原因**: 零依赖，Linux 原生，Mason 一人运维足够
- **天花板**: 复杂依赖图（DAG）、并行任务合并、跨机器调度、错误处理脆弱
- **当前状态**: 刚加入 event_router.py + dispatcher.sh，覆盖简单链式触发
- **替换条件**: agent 数量 >30 且出现任务依赖死锁，或需要跨 GCP/阿里云调度
- **替换方案**: Celery（已有 Python 生态）或 Temporal（更适合长事务）

### 组件: inotify + queue.jsonl（事件队列）
- **选择原因**: 零依赖，单机延迟 <1s，今晚就能建好
- **天花板**: 并发写入 >10/s 时文件锁竞争，跨机器失效，无消费确认机制
- **替换条件**: agent 数量 >20 且出现竞争问题，或需要阿里云→GCP 事件传递
- **替换方案**: Redis Streams（轻量）或 RabbitMQ（重量但可靠）

## 存储层

### 组件: 文件系统（JSONL + markdown）
- **选择原因**: 人类可读，git 可追踪，零运维
- **天花板**: 关联查询慢（需全文扫描），无索引，无权限控制
- **当前用途**: audit.jsonl、queue.jsonl、reports/、intel/
- **替换条件**: 单文件 >100MB 或需要跨表关联查询（如"过去 7 天 EMP_0008 所有失败"）
- **替换方案**: SQLite（已在用，扩展即可）→ PostgreSQL（多用户时）

### 组件: SQLite
- **选择原因**: 嵌入式，零运维，单文件备份
- **当前用途**: kbeauty.db（素仁轩）、scout.db、tracker.db、MediaCrawler
- **天花板**: 并发写入（WAL 模式下 ~50 writer/s），无网络访问
- **替换条件**: 需要多进程并发写入，或多机器访问同一数据库
- **替换方案**: PostgreSQL（阿里云 RDS，月费 ~¥50）

## AI 层

### 组件: Claude Code（claude -p）
- **选择原因**: Agent 执行的核心引擎，直接操作文件系统
- **天花板**: 无法常驻（session-based），嵌套调用受限（CLAUDECODE=1 检测）
- **当前约束**: 每次 session ~500MB 内存，GCP 3.8G 限制同时 ~6 个
- **替换条件**: 需要常驻 agent（event-driven 实时响应）
- **替换方案**: Claude Agent SDK（常驻进程）或 Claude API + 自建 runner

### 组件: 多模型策略（DeepSeek/Gemini/Qwen）
- **选择原因**: 成本分层（DeepSeek 便宜做分析，Gemini 做多模态，Qwen 做交叉验证）
- **天花板**: 3 套 API 的统一管理，模型间一致性难保证
- **替换条件**: 单一模型能覆盖所有场景且成本可接受
- **替换方案**: 短期不替换，长期关注 Claude 降价

## 基础设施层

### 组件: GCP（指挥中心）+ 阿里云（生产）
- **选择原因**: GCP 开发方便，阿里云贴近中国用户和 XHS
- **天花板**: 跨云数据同步（当前 scp cron），网络延迟
- **当前方案**: 方案 A 文件同步（data-sync.sh），>50MB 时升级方案 C（API 网关）
- **替换条件**: 数据量 >50MB 或需要实时双向同步
- **替换方案**: 方案 C（阿里云 FastAPI + GCP data_client.py SDK）

## 技术栈保质期评估

| 阶段 | 时间线 | 现有栈够用？ | 需要补什么 |
|------|--------|-------------|-----------|
| Phase 1（单人深化） | 0-18 月 | ✅ 够用 | 专注深化能力，不换栈 |
| Phase 2（多城市） | 18-36 月 | ⚠️ 部分 | +API 层 + 任务队列 + 权限系统 |
| Phase 3（平台化） | 36+ 月 | ❌ 需重建 | 多租户 + SLA + 计费，全新设计 |

**核心结论**: 现在不需要换栈。每个组件都有明确的天花板和替换条件，到了再换。
限制发展的从来不是技术栈，而是对系统的认知深度。
