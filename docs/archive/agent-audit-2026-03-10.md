## 关键发现

### 系统性盲点：下游通知层最弱

14 个 Agent 中，只有 5 个明确定义了完成后触发什么事件。
9 个 Agent 做完就走，不管下游。这就是"A 完成 → B 不知道"的根因。

**最严重的缺失**:
- **EMP_0010 Content Creator** — 产出内容后不发任何事件，EMP_0008 不知道内容就绪
- **EMP_0011 Account Manager** — 更新 brief 后不通知消费者，下游 agent 读的可能是旧 brief

### 触发条件：Dev 类全是被动的

EMP_0002/0005/0009 三个 Dev agent 没有任何自主触发条件，只能被 `/dev-task` 手动启动。
这是 Pull System 的第一个阻断——执行层不知道有活干。

**修复方向**: Dev agent 应该声明"我监听 task-assigned-to-me 事件"，dispatcher 分配任务后写事件触发。

### 输出契约：一半是隐含的

7 个 Agent 的输出是隐含的（"更新 Slack"、"修改文件"），没有明确格式。
这导致 Manager 无法结构化地聚合下属汇报。

**修复方向**: 统一汇报 JSON 格式（已在模板中定义），每个 agent 完成后写 `/data/reports/`。

### 前置条件：整体最好

12/14 有明确的启动加载流程。这是之前设计做得最扎实的部分。

## 修复优先级

按影响面排序：

| 优先级 | 修复项 | 影响 | 涉及 Agent |
|--------|-------|------|-----------|
| 1 | 统一汇报 JSON 格式 | 所有 agent 都需要 | 全部 14 个 |
| 2 | Dev agent 事件触发 | 解锁 dispatcher → Dev 自动接活 | 0002/0005/0009 |
| 3 | 下游事件声明 | 补齐"做完后通知谁" | 0010/0011/0003/0014 |
| 4 | 输出契约显式化 | Manager 能结构化聚合 | 0000/0003/0004/0008/0013/0014 |

## 与 Event Trigger 的关系

Event Trigger（event_router.py）要工作，需要两个前提：
1. **事件生产者** — 每个 agent 完成后写事件 → 对应"下游通知"层
2. **事件消费者** — 每个 agent 声明监听哪些事件 → 对应"触发条件"层

这两层恰好是当前最弱的两层。补齐它们 = 补齐 event trigger 的基础设施。
