# Dev 执行协议（跨 Agent 共享）

无状态 Dev agent（EMP_0002/0005/0009）的标准任务执行流程。

## 代码类任务（修复 bug、新增功能、重构）
1. 先读现有代码，理解当前逻辑
2. 规划修改方案（影响哪些文件，有无副作用）
3. 执行修改——保持修改最小化，只改任务要求的部分
4. 强制验证（不可跳过）：
   ```
   ~/mason-hub/skills/dev-tools/dev-verify-loop.sh <修改的文件,逗号分隔> <测试模块名>
   ```
   脚本自动执行：语法检查 → 模块测试 → 全量回归。
   验证失败 → 读错误 → 修复 → 重跑，最多 3 次。
   3 次仍失败 → 汇报 task_failed，附完整验证输出。
5. 验证通过后汇报完成并附验证结果

## 分析类任务
1. 明确分析目标和输出格式
2. 收集数据 → 执行分析 → 区分"事实"和"推断"
3. 汇报完成，附分析结果

## 排查类任务
1. 收集信息（日志、代码）→ 定位问题 → 分析根因
2. 执行修复 → 验证修复有效（同代码类验证）
3. 汇报：问题原因、修复方案、验证结果

## 完成汇报
- 做了什么（1-2 句话）、修改了哪些文件、验证结果、insights（意料之外的发现）

## 失败汇报
如实汇报：文件不存在、测试不通过且 3 次修复失败、需要范围外文件、外部服务不可用。

## 代码修改规范
- 先理解再改，保持修改最小化，不做"顺便优化"
- 发现其他问题记 insights，不自行修复
- 不删文件除非明确要求

## Escalation（3 轮验证失败时，run-agent.sh 自动处理）
1. `git checkout -- .` 恢复代码
2. 写入失败摘要到 `~/mason-hub/logs/audit.jsonl`
3. Slack 通知
4. 等待 PM 评估

**你的失败汇报必须包含**：每轮错误信息、根因判断、尝试过的修复方向、建议的正确方向。

**NEVER**：绕过验证、伪造结果、3 轮后继续改代码、跳过 PM 直报 Mason、改测试文件让测试过、隐瞒失败信息。
**ALWAYS**：如实汇报、分析上轮失败原因再修、超出范围第 1 轮就说明。

## 重试任务处理
收到 PM 重新分配时：读"上次失败根因"和"本次调整方向"，不重复上次思路。标注"第 2/2 次分配"意味着最后机会，选最保守方案。
